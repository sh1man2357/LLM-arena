# 项目目标与版本范围

## 目标

让模型各自生成一个代表自身策略和编程能力的 Bot，在相同规则、资源限制和开发机会下比较实际比赛表现。

观赛是项目的重要组成部分：人应能直观看到模型 Bot 的行动，检查关键时刻，并从比赛证据理解结果。确定性引擎负责可信竞争，交互前端负责把竞争变成可观看、可探索的体验。

实验链：统一任务包 → 模型编写代码 → 代码冻结 → 编译与资格检查 → 隐藏地图比赛 → 名次与辅助统计 → 长期评级与 Baseline 校准。

竞技场测量的是模型在指定开发协议下生成有效策略程序的能力。一次 Bot 提交不能完整代表模型的所有能力；模型本身的生成波动、语言熟练度和开发工具使用也会影响结果。

## 第一版交付内容

1. 确定性炸弹人规则引擎，支持两个 Bot 同时行动。
2. 根据 Seed 生成合法地图，进行出生位交换。
3. C++20 SDK、编译脚本和受限 WASM 执行器。
4. Random、Safe、Heuristic 三个冻结的 Baseline。
5. 无界面的单局和批量比赛入口。
6. 机器可读结果、胜负平统计和平均名次分。
7. 逐 Tick Replay、文本回放和复现校验。

v0.1 的验收范围不含图形观赛；该能力现在纳入 v0.2 核心交付。多人正式排名、道具、雾、缩圈和学习训练继续后置。规则引擎及协议为多人扩展保留空间，但不能把尚未验收的多人能力写成已支持。

## v0.2 交付方向

1. 统一视觉、高完成度交互的观赛前端：真实直播、图形 Replay、时间轴、事件定位与对象检查。
2. 比赛大厅与主办方控制台：创建单局 / 批次、监看调度、停止、恢复与失败重试。
3. 60 分钟收卷与资格工作台：导入单份源码、提前冻结、编译、日志和失败记录。
4. 批次榜单和行为分析：配对、出生位、地图、置信区间、故障和平局解释。
5. 本地 API、持久作业、旧证据兼容、公开导出及一键启动。

完整范围、配套能力的开发取舍和后续工作包见 [v0.2 产品规划](./08-v0.2-plan.md)，实际验收见根目录 [DELIVERY_v0.2.md](../DELIVERY_v0.2.md)。历史观赛、收卷冻结、异步编译、调度与真实直播的基本闭环已有实现；完整恢复、发布交接、视觉与性能验收仍待完成，不能将部分实现视为整版交付。

v0.2 默认沿用 v0.1 双人规则，不同时引入缩圈、道具或长期 Rating。先分析大量平局的原因，再为后续玩法版本形成可验证建议。批次榜单只描述相同对手池，不冒充跨版本长期排名。

## 建议玩法边界

- 全图信息公开；Bot 只能看到规则规定的公共游戏状态和自身内存。
- 地图包含道路、不可破坏墙和可破坏墙。
- 无道具；整个比赛期间炸弹容量和爆炸范围固定。
- Bot 每 Tick 执行一个动作：等待、四方向移动或放炸弹。
- 爆炸致死，最后存活者获胜；到达最大 Tick 时，剩余存活者并列。
- 不主动强制进攻。长期等待导致平局是该版本允许的结果，需要在 Baseline 比赛中观察其影响。

## 设计原则

游戏规则必须先于策略实现固定，不能为某个 Bot 的结果临时调整。观察信息、动作验证和计算预算对所有 Bot 相同。

模拟推进只使用整数 Tick，不使用系统时间。渲染速度和执行先后不改变游戏顺序。需要变化规则时，创建新版本并重新运行完整比赛。

Bot 的源码、WASM、SDK、编译器、运行时配置和地图版本都属于成绩的来源证据，必须保留哈希与配置。

## 第一版完成标准

在同一冻结清单下，三个 Baseline 可以编译并完成比赛；同一局重复运行产生相同状态和动作记录；50 个地图 Seed 对每个 Bot 配对各换边一次，结果完整；Replay 能验证最终结果。无限循环、非法动作和崩溃 Bot 的行为符合故障规范。

有策略差异不等于已经证明排行榜有效。首版验收首先证明实验过程可运行、可复现、可解释。
