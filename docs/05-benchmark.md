# 评测与评分规范 v0.1 草案

## 统一开发协议

每次评测发布一个任务包，包含相同 Prompt、规则、SDK、模板、公开地图、测试工具和提交要求。不同模型必须获得相同的信息和操作机会。

正式运行前必须填写并冻结以下配置，未填完整的试跑只能称为开发实验：

| 字段 | 必须记录的内容 |
| --- | --- |
| 模型 | 完整模型标识、提供方、请求日期、支持的生成设置 |
| 任务输入 | 原始 Prompt 与任务包哈希 |
| 生成限制 | 每次输出上限、总 token 预算及其计量方式 |
| 开发工具 | 是否可以编译、运行、读取日志、使用网络或外部资料 |
| 修改机会 | 固定修改次数，或统一累计开发预算 |
| 反馈 | 每轮允许看到什么错误和公开测试结果 |
| 截止条件 | 提交时间、预算或迭代上限，不能按结果临时延长 |
| 生成重复 | 每个模型独立提交几次，如何汇总与展示 |

不同提供方的 token 定义、推理预算和工具能力可能不同。应公开实际配置，不能只因给了相同数字就宣称所有开发成本完全相等。无法严格统一的因素写入评测限制。

第一版建议使用受控开发模式：统一环境，只允许 SDK 与公开地图；允许固定次数的编译和测试反馈；禁用正式地图访问；源码冻结后不再修复某个模型的 Bot。具体次数与 token 上限在调用模型前确定。

实现者手写 Baseline 的开发过程与模型协议不同，因此 Baseline 是参照程序，不是另一模型的公平开发结果。

## 代码冻结与参赛资格

先归档源码并计算哈希，再使用统一工具链编译和检查。参赛者唯一键是提交标识，不是模型显示名称。

编译失败或 ABI 不合格的提交保留失败记录，展示参赛资格失败比例，不进入正常比赛均分。不能只删除失败提交而不报告，否则会掩盖模型的编程失败率。

资格通过后冻结 WASM 哈希。任何源代码、SDK 包装器或编译参数变更都产生新提交，不能沿用旧成绩。

多次独立生成的 Bot 分别作为 entrant 参赛；报告生成间差异。不得事后只挑最好 Bot 代表模型，除非事先定义统一选拔协议，并用独立测试集评价选拔结果。

## v0.1 比赛调度

至少准备 Random、Safe、Heuristic 三个 Baseline。其中 Heuristic 计划作为未来 Rating 展示零点。更强 Baseline 可以后续增加。

每对参赛者使用同一份 50 地图案例清单；每个案例进行两局出生位交换，共 100 局。批量运行结果必须写回完整调度表，不能因失败或表现异常静默跳过某局。

基础设施失败单独计数，修复后用相同清单重跑；原失败日志保留。正式汇总只接受完整有效调度，缺失时标为 incomplete。若失败源于版本变更，全部受影响比赛重新运行。

第一版比赛单位是单局，地图案例单位是两局换边组合。多个参赛者采用全配对 round robin，并包含 Baseline 对局。未来加入新 Bot 时，对手池变化会改变汇总均分，不能直接把不同对手池的均分当作相同尺度。

## 核心单局名次分

设本局有 N 个 Bot，N ≥ 2。对 Bot i 和每个对手 j，定义：

```text
pair_result(i, j) = 1     i 存活更久
                  0.5   两者并列
                  0     j 存活更久

placement_score(i) = sum(pair_result(i, j), j != i) / (N - 1)
```

这里“更久”按游戏规则的存活/死亡 Tick 判断。胜者存活高于已死者；上限时仍存活者互相平局；同 Tick 死亡者互相平局。

无并列的 5 人局分数为 1、0.75、0.5、0.25、0。若前两名并列，两者均为 `(3 + 0.5) / 4 = 0.875`。双人局等于胜 1、平 0.5、负 0。

不同人数的分数范围相同，但比赛难度和交互结构不同。未来合并不同人数结果时，需要预先冻结人数权重和对手抽样规则；仅做归一化不保证不同赛制分数可直接比较。

## 第一版输出与不确定性

每个配对输出胜、负、平、有效局数、两个出生位的分别表现、平均名次分，以及每张地图的换边组合结果。多对手汇总对每个对手等权，避免因调度次数不同产生偏置。

建议使用地图案例为抽样单位的固定 Seed bootstrap：先对一张地图的两局取均值，再重采样地图案例 2,000 次，报告均值的 95% percentile 区间。地图数量太少时仅展示描述统计并注明限制。固定 bootstrap Seed、实现版本和插值方法，保证报告可复现。

这个区间反映所抽地图的变化，不涵盖模型重新生成代码的全部波动；后者需要独立生成重复。对同一确定性配置无限重复同一局不会增加新的地图证据。

辅助统计至少包括：平均结算 Tick 数、爆炸死亡数、单一归因击杀/自杀、混合归因死亡、动作故障次数、fuel 耗尽次数、故障淘汰率和初始化失败率。明确分母，不能把崩溃淘汰归为自杀。

## 长期 Rating 与 Baseline 零点

第一版不选择或实现长期 Rating。后续需比较多人评级算法及其对平局、非传递克制、赛程和不确定性的处理，再冻结算法、参数与更新顺序。

选定算法后，展示分可定义为 `rating(bot) - rating(reference_baseline)`。必须同时发布原始 Rating、参考 Baseline 哈希及误差估计。不要提前赋予“+200”固定胜率含义；它取决于评级模型。

保留固定 Baseline 便于后续校准，但 Baseline 本身不保证跨规则版本可直接比较。规则、地图分布或对手池变化都可能改变成绩含义。

## 版本与发布证据

每次运行清单包含 benchmark_id、ruleset、map_generator、sdk、compiler、runtime、fuel 配置、baseline_set、任务包哈希、提交哈希、Seed 清单承诺哈希、调度哈希和报告算法版本。

正式 Seed 清单在比赛前生成，采用规范化 JSON 字节及 SHA-256 留下承诺。公开时提供原文件和哈希；保密期间可公开承诺哈希。不得看完结果再删除“异常地图”或选择有利 Seed。

重要组件或计分规则改变时建立新 benchmark_id。选择展示 Replay 时注明筛选方式，并提供完整原始结果；单场精彩录像不能代表整体实力。
