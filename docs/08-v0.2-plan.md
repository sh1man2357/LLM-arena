# v0.2 产品规划：从可运行到可观赛

状态：规划已编写，尚未开发或验收。对应交付标准见根目录 [DELIVERY_v0.2.md](../DELIVERY_v0.2.md)。

## 版本目标

项目既要比较模型编写策略程序的能力，也要让人看懂模型之间的竞争。v0.1 已经建立可复现的比赛闭环；v0.2 把它变成一个完整的本地观赛产品：比赛能从界面组织，运行过程可观看，结束后可回放、比较并解释结果。

观赛前端是本版本的核心交付，视觉质量、交互质量与规则真实性一起验收。只有静态展示页、播放演示动画或薄层命令行包装，不能视为完成。

v0.2 默认沿用双人 v0.1 的规则、地图生成器、SDK、fuel 和评分公式。产品版本升级不意味着玩法升级；正式比赛仍只执行已冻结的 Bot，不在线调用模型。

## 为什么同时开发这些内容

| 交付方向 | 当前缺口 | v0.2 的结果 | 优先级 |
| --- | --- | --- | --- |
| 图形观赛与回放 | 目前只有文本回放，难以理解空间与时序 | 统一的比赛画面、播放器、事件时间轴、玩家检查器 | 核心必需 |
| 比赛大厅与控制台 | 比赛靠 CLI，结果分散在文件夹 | 浏览比赛、发起对局和全配对、查看进度、恢复中断 | 核心必需 |
| 提交与参赛管理 | 已有任务书和编译器，缺少收卷界面 | 导入源码、60 分钟交卷记录、资格检查、冻结版本 | 核心必需 |
| 对战分析与榜单 | 已有报告算法，缺少可交互的解释 | 批次内排名、配对矩阵、地图换边对比、故障与平局分析 | 核心必需 |
| 本地服务与交接 | 尚无浏览器可用的数据 / 作业接口 | 一键启动、异步作业、持久状态、可复核导入导出 | 核心必需 |
| 首次真实模型展示赛 | 尚未收到 / 运行真实模型提交 | 使用 60 分钟协议收卷，再运行新的隐藏案例 | 支持；实际收卷另记运行成果 |
| 长期 Rating | 尚未选算法和验证跨赛季可比性 | 本版先展示有边界的批次成绩 | 后续版本 |
| 玩法区分度改进 | Heuristic 对 Safe 的验收配对有 94/100 平局 | 分析停滞、进攻与故障证据，形成下一版规则建议 | 分析必需；改规则后置 |

首次真实模型展示赛依赖外部模型与实际提交，不能用伪造参赛数据替代。v0.2 工程验收必须支持从手工收卷到展示比赛的完整路径，但不要求购买服务、获得账号或自动调用提供方 API。

## 三种使用路径

### 观众：进入比赛并看懂结果

打开大厅 → 选择进行中比赛或历史对局 → 看地图与双方状态 → 暂停 / 逐 Tick 查看关键事件 → 打开同一地图的换边局 → 查看配对及批次成绩。

观赛页始终显示参赛者名称、出生槽位、当前 Tick、比赛状态。结束画面说明胜负和平局原因；不能把爆炸死亡、动作故障淘汰和基础设施失败用同一种动画 / 文案带过。

### 主办方：收卷并组织比赛

分发现有 [MODEL_TASK.md](../MODEL_TASK.md) → 为模型记录发卷时间 → 在 60 分钟内接收一个最终 `bot.cpp` → 立即冻结源码 → 统一编译和资格检查 → 选参赛池和案例集 → 固定调度 → 启动与监看 → 校验后发布成绩。

没有额外的 token 或修改轮数表单。提前交卷即冻结；截止时间不因编译错误延长。编译、资格失败与未交卷都有记录。手工录入的发卷 / 收卷时间须注明记录来源，不将界面计时器当作已经验证了远端模型的实际开发时间。

### 研究者：解释 Bot 行为

筛选对局 / 地图 / 胜负 / 故障 → 检查动作与事件 → 查看炸弹 owner 与到期 Tick → 比较双方 fuel 和失败类别 → 查看同地图换边组合与置信区间 → 导出报告与公开 Replay。

分析不推断 Bot 的内部意图。“没有放弹”“移动失败”“某个 owner 的爆炸覆盖了玩家”可以由记录证明，“模型想埋伏”不能作为事实展示。

## 核心功能边界

### 观赛

必须支持离线历史 Replay 和正在执行的对局。直播来自宿主已提交的实际状态；暂停、变速与跳转只影响本地播放，不影响引擎或其他观众。

必须支持播放 / 暂停、初始帧、首尾、前后单步、0.25 / 0.5 / 1 / 2 / 4 倍速、可拖动时间轴、事件定位、双方选择、炸弹检查、全屏、键盘和触屏操作。直播可回看已接收帧，并通过“回到最新”跟随运行进度。

回放与直播复用同一播放器和场景系统。界面不能把到期 Tick、爆炸覆盖、软墙清理或并列死亡渲染成另一套规则。

### 比赛管理

大厅提供进行中、待运行、已结束、失败 / 中断及历史批次入口。支持按参赛者、批次、状态与结束原因筛选，并保留 URL 状态。

主办方可发起双人单局和全配对批次。批次默认 50 案例 × 每对换边两局；调度冻结后不能直接编辑参赛池或 Seed。进度显示已完成 / 总局数、失败数及当前对局，不能把播放帧数当作比赛执行进度。

支持排队、在当前单局结束后停止调度、恢复、重试基础设施失败。UI 的暂停播放与主办方的停止调度是两个有明确名称的操作；未执行完的批次保持 incomplete。

### 收卷与冻结

支持粘贴 C++ 源码、上传单个 `bot.cpp` 和导入已有冻结提交。每份提交有独立 ID、显示名称、模型标识、时间记录、源码 / WASM 哈希、编译日志及资格状态。

编译是异步作业，不能阻塞大厅或播放器。主办方可以在界面阅读原始错误；交卷后的代码不可覆盖，更正产生新提交且不能混入同一正式收卷结果。

模型生成仍可在外部对话完成。本版收卷由本地主办方操作，不引入公开互联网上传服务、多用户账号系统或模型 API 自动代理。

### 成绩与分析

榜单的范围是同一冻结批次和对手池，列出平均名次分、胜负平、有效局数、出生位表现和资格失败；分数并列保持并列，不用击杀或展示顺序破同分。

提供配对矩阵、换边对比、地图案例明细、故障分类、平均时长、放弹 / 爆炸死亡 / 归因统计和已有 bootstrap 区间。样本不足时显示限制，不绘制伪精确区间。

不完整批次展示进度、单局事实和“暂定”标识，不发布正式汇总排名。不得把不同对手池的分数拼成通用全球榜单，不把批次均分称为 Elo 或长期 Rating。

平局分析分出时间上限存活、同 Tick 全灭、初始化全败等已知原因，并提供时间轴和放弹 / 移动统计。不得为减少平局而重写既有比赛或修改计分。

### 数据发布

支持导入旧 Replay / 批次和导出公开报告、公开 Replay、当前画面 PNG，以及定位到某对局 / Tick 的链接。链接在本地实例有效，不暗示已经发布到公网；MP4 / GIF 录制后置。

正式隐藏集默认封存。展示完整地图或 Replay 本身就泄露地图，不是只移除 Seed 就能保持未见。正式直播 / 发布前，关闭该参赛池的收卷窗口并记录案例披露状态；后续新提交必须使用新的隐藏集。详见 [服务架构](./10-v0.2-service.md)。

## 视觉与体验要求

采用“竞技转播台”的统一方向：克制的深色舞台、清晰的比赛网格、稳定的参赛者识别、精确的数字和充分留白。地图是视觉中心；大厅、榜单、提交和日志使用同一套字体、颜色、组件与动效规范。

“审美顶级”通过设计系统、关键页面高保真方案、真实数据截图及逐项人工走查落实，而不是用框架或主题名称代替。具体颜色、布局、状态、动作与 QA 标准见 [前端体验与视觉规范](./09-v0.2-frontend.md)。

## 不纳入本次必需交付

3～8 人正式赛制、道具、缩圈、雾、训练、自适应 Bot、长期 Rating、云端托管、账号权限平台、支付、聊天 / 弹幕、提供方 API 自动编排、视频录制都留待后续。

规则变化可能值得开发，但应先用本版分析定位区分度问题，提出独立规则版本，再做固定新案例验收。不因观赛需要让游戏世界跟随墙钟、特效或浏览器帧率推进。
