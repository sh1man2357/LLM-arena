# 地图与随机性

## 地图生成器

地图采用 13 × 11、180° 旋转对称地图，双人出生点为 `(1,1)` 和 `(11,9)`。对称性减少初期公平性变量，出生位交换仍然必做。

生成步骤必须严格固定：

1. 外边界全部为不可破坏墙。
2. 内部 x、y 都为偶数的格子为不可破坏墙，其余为候选道路。
3. 每个出生点曼哈顿距离 ≤ 2 的非硬墙格强制清空；出生点自己、两个相邻出口及各自第二步道路均可用。
4. 对剩余非硬墙、非强制清空格按 180° 对称关系划分轨道。每个轨道以行优先索引最小的格子为代表；代表按索引升序处理。
5. 每个轨道只取一个 RNG 输出 r；当 `r < 2362232012` 时，将整个轨道置为可破坏墙，否则置为道路。约 55% 的候选轨道放软墙。
6. 完成合法性检查。失败则重新构造候选地图，继续使用同一 RNG 流，不重新初始化。

对称变换为 `(x,y) → (12-x,10-y)`，单格轨道也只抽取一次随机数。强制清空格和硬墙不消耗随机数。

合法性检查：出生点及其两个出口是道路；每个出生点初始可达道路不少于 5 格；两个初始区域大小相同；把软墙视为可通行后，所有非硬墙格和出生点连通；全图保持旋转对称。

最多尝试 256 张候选地图，仍不合法则返回地图生成错误。不得在运行时替换 Seed 或使用不公开的备用地图。重试次数记入地图元数据。该构造通常直接满足检查，检查仍用于防止实现偏差。

## 固定 RNG

MapGenerator 使用 xorshift32，仅用于可复现地图生成，不用于密码学：

```text
输入 seed 为 uint32。
state = seed；若 seed = 0，则 state = 0x6D2B79F5。
next_u32():
    state ^= state << 13
    state ^= state >> 17
    state ^= state << 5
    return state
```

每步使用 32 位无符号整数，左移溢出按模 2^32 截断，右移为逻辑右移。Seed 0 和替代值产生相同地图；正式列表禁止同时使用这两个 Seed。验收时还应剔除重复地图哈希，避免不同 Seed 对应同一地图被重复计权。

Bot 使用独立 64 位种子，其来源与地图生成流分离。SDK 可以提供固定的整数 PRNG 帮助函数，也允许 Bot 根据传入种子自行实现可复现随机策略。

## 种子清单与出生位轮换

公开开发集建议包含 10 个不同地图 Seed，发布地图、状态样例与运行方式。正式双人集建议包含 50 个不同地图，地图 Seed 在源码冻结前保密。

正式运行前创建并锁定完整种子清单。每个地图案例包括 map_seed 和两个独立 bot_seed；bot_seed 不由 map_seed 直接转换，避免 Bot 从初始化种子反推正式地图 Seed。

对于按 entrant_id 排序的 Bot 配对 A、B：同一地图的第一局 A 在槽位 0、B 在槽位 1；第二局交换槽位。两个 bot_seed 分别分配给 A 和 B，在换边局中跟随参赛者，不能跟随槽位。所有配对使用同一案例列表和种子分配规则。

保存 seed 不是唯一复现条件。重跑 Bot 必须同时固定规则、生成器、SDK、WASM、运行时及 fuel 配置。只播放记录好的 Replay 不需要再次执行 Bot。

正式 Seed 可在整个赛季提交窗口结束后公开；如果仍允许新提交并希望维持隐藏测试，应继续保密。展示 Replay 必然泄露部分地图，此类地图以后不能再宣称为完全未见测试案例。 正式观赛须在对应参赛池收卷关闭后开放。服务记录案例由封存到披露的状态；即使公开副本删掉 Seed，完整棋盘仍然披露地图。后续新提交使用新的隐藏案例，具体发布边界见 [本地服务架构](../architecture/service.md)。

## 多人后续扩展

3～8 人正式评测需要新的出生槽位方案、地图合法性约束和轮换调度。不能直接在双人地图中随机插入出生点。

至少要求每个参赛者同等次数占用各槽位，并平衡对手邻接关系；仅做循环位移未必足够。多人地图及调度是后续版本的独立验收项。
